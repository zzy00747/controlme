# Code Review 规范(Android / Kotlin)

> 适用范围:ControlMe 的 Bug Fix、功能改动、架构调整。
>
> 定位:一套帮助作者和 reviewer 判断问题的通用机制,**不规定具体类型、字段、状态枚举、存储方式、文件数或代码行数**,也不是用 checklist 代替工程判断。

## 目标

Review 不应只确认「PR 描述里的 case 已消失」,还要判断:

- 这是一个局部实现错误,还是系统机制缺失?
- 修复是否落在真正负责的边界?
- 方案是在消除一类问题,还是只给当前症状加补丁?
- 改动和验证是否覆盖了真实影响范围?

「最小改动」指恢复正确行为所需的最小完整改动,不等于文件最少或代码行数最少。

---

## 七个通用 Review 机制

### 1. 先说清系统原本应该保证什么

先区分「用户看到的症状」和「系统被破坏的行为约束」。

能回答:在什么情况下,系统应该或不应该发生什么。只写「页面展示不对」「这里缺判断」「LLM 没按提示词走」通常还只是症状。

如果作者和 reviewer 尚未对正确行为达成一致,不应直接讨论字段、分支或类型设计。

### 2. 建立因果链,不要从症状跳到改法

从真实入口沿运行链路追踪,找到第一个错误决定或错误状态:

```
入口 → 产生或决策 → 保存或传递 → 消费 → 用户或外部效果
```

例(本项目):`对话输入 → LLM 解析 → DraftStateMachine 流转 → SessionCoordinator 落库 → 计划列表消费`。
如果方案直接在新的 `if` 分支补判断,却没有说明错误状态从哪里产生,通常还没找到根因。

### 3. 确认责任层和单一事实来源

判断哪一层拥有做出该决定所需的完整信息,修复应优先发生在该层,并明确哪份状态是 source of truth。

- 本项目里,`SessionCoordinator` 是「确认→落库」的唯一权威入口;UI 可以展示状态、ViewModel 可以催促提交,**但不能各自重新推断业务状态**(例如在 UI 层造第二个「是否已确认」标志)。
- 下游可做防御性校验与 fail-closed,但不能再次推导同一业务规则。

### 4. 先审计已有机制,再新增机制

新增字段、枚举、fallback、特殊分支前,先搜索已有相邻抽象和全部调用点,回答:

- 现有机制是否已表达相同或相近的概念?
- 如果不能复用,缺失的语义到底是什么?
- 新旧机制边界是否冲突或重复判断?

例:草稿已有 `update_draft` 流程,新增「改标题」时先看它能否复用,不要在旁再造一套平行路径。

### 5. 检查完整生命周期和相关风险

不要只看 diff 或当前成功路径。沿相关生命周期检查:产生、持久化、传输、实时消费、刷新/恢复、历史数据、最终外部效果。按改动性质挑选风险:

- Room 数据会被哪些消费者使用(计划列表、进度聚合、提醒)?
- 失败 / 超时 / 结果不确定时会发生什么(LLM 15s 超时、用户中断)?
- 涉及副作用时,系统是否知道它有没有执行,是否允许重复(WorkManager 提醒、重复调度)?
- 旧数据、缓存、在途任务、混合版本是否安全(Room 迁移、`DATASTORE` 版本)?
- 依赖方向是否被破坏(`domain` 是否被拖入 Android 依赖)?

### 6. 用一个完整责任控制 Scope

一个 PR / 一组联动 PR 应围绕一个能清楚说明的行为约束。可独立验收、回滚或发布的行为应拆开;但同一跨层契约不能为了「PR 看起来小」被拆成部署后短暂失效的半套修复。文件数、行数只是追问信号,不是质量结论。

### 7. 用行为证据证明修复

测试和验证应证明系统行为恢复,而不是只证明新 helper / 字段 / 分支被执行。

- Bug Fix 尽量给出「修改前可复现、修改后通过」的证据,走最接近真实行为的入口。
- 状态机测试应直接验证「未 COMMIT 不写库」这一行为结果,而非只断言某个内部方法被调用。
- 无法稳定自动化的边界要明确说明,并给出替代证据和未验证范围;测试变绿不能替代对责任层和产品语义的判断。

## PR 提交前自测

相关 PR 在 Body 中回答下列问题,简单改动每项一两句话,风险越高证据越具体:

```
Expected behavior / broken constraint:    本该保证什么行为
Observed symptom and reproduction:         症状与复现(如为修复)
Causal chain and first wrong decision:     因果链与第一个错误决策
Authoritative owner / source of truth:     责任层 / 唯一权威状态
Existing mechanism considered:             审计过的已有机制
Affected path, risks and scope:            影响范围与风险
Verification and unverified boundaries:    验证了什么、未验证什么
```

模板见 `.github/pull_request_template.md`。

## 需要停下来重新分析的信号

下面情况不代表某种实现一定错误,但**默认应暂停继续堆代码**,回到七个机制重新判断:

- 根因只是换一种方式复述页面现象或错误信息。
- 同一规则需要在多个下游 / 多个展示路径分别实现(UI 和协调器各写一份「是否已确认」)。
- 新增概念与已有字段或抽象相近,却没说明语义边界。
- 上游持续产生含混数据,依赖下游逐层隐藏、清洗或猜测。
- 权威状态(某任务是否已 `done`)来自模型、文本、历史记录或「最新值」的反推,而非 Room 单一来源。
- 必须保证的行为只依赖 prompt、UI 文案或团队约定,没有执行层约束(如「未确认不落库」必须落在协调器代码层)。
- PR 同时处理多个可独立验收或回滚的问题。
- 测试只断言实现细节,没有证明最终行为或关键反例。

Reviewer 因此阻塞 PR 时,必须明确指出违反了哪条行为约束、证据在哪里、实际后果是什么;不能只引用本清单或个人偏好。

## 专项 Review

命中高风险领域时,进入对应专项(未建立则从本规范继承原则):

- **状态机 / 落库**:草稿生命周期 `NEW→DRAFT→COMMITTED|MEMO|丢弃`,重点审「未确认不落库」「落库后才可打勾」两条不变量。
- **LLM 协议**:tool-calling schema 输出、未确认不落库、超时中断后的草稿稳定性。
- **Room 迁移 / 并发**:迁移脚本、事务、协程并发写。

稳定下来的领域规则写入对应 `docs/adr/`,不要不断扩张主文档。

## Review 输出格式

建议 findings first:

```text
Findings
1. [P1] 标题
   Evidence: file:line -> file:line
   Broken constraint: 系统原本应该保证什么
   Why it matters: 实际运行后果
   Direction: 应回到哪个责任层重新设计或修复

Verification
- 已验证的路径
- 未验证的边界
```

Reviewer 不需要替作者设计完整方案,但需把问题定位到正确的行为约束和责任层;作者负责给出完整、可验证的修复。
